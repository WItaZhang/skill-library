# Skill Library 开发需求与模块任务

本文用于产品、设计、前后端和 Agent 平台开发共同实施第一版 Skill Library。目标是让非技术用户在平台中使用 Skill、提出修改、完成评审，并在更新后继续安全执行任务。

状态：可进行模块拆分与基础开发；第 3 节中的产品默认规则需要确认后才能作为最终验收口径。平台已有线上 Agent 执行环境，本项目负责 Skill 管理及其运行时接入，不重建通用 Agent 执行引擎。

## 1 已确认的产品要求

- 面向非技术用户，主要暴露使用、修改、评审、历史版本和会话更新提示。
- Skill 在平台的 Agent 环境中直接调用，不以本地安装或下载为主要流程。
- 每人独立修改并提交评审，再合并；不支持多人实时共写。
- 每个 Skill 指定维护者；作者不能批准自己的修改。
- 批准并合并后立即生成生效版本，不增加独立发布审批。
- 默认情况下，所有人的新任务采用最新版；进行中的任务固定原版本，包括该任务的重试与恢复。
- 用户能查看 Skill 历史版本。
- 会话中已经调用的 Skill 更新后，要提醒用户，并提供使用新版或保留原版的选择。
- 不设计订阅、订阅通知、通知中心或邮件等外部通知。此前讨论的订阅方案已取消。

## 2 范围与用户操作

### 2.1 第一版范围

包含团队内 Skill 列表与详情、使用入口、独立草稿、修改提案、评审合并、冲突处理、不可变历史版本、任务版本固定、会话更新提示和版本选择，以及必要的权限、审计和故障恢复。

不包含实时共写、跨团队公开市场、本地同步、订阅体系、独立发布流程、自动语义冲突解决、完整的 Agent 引擎开发。脚本运行能力沿用现有平台；本项目不得绕过现有工具和执行权限。

### 2.2 界面语言

| 用户操作 | 界面用语 | 系统含义 |
| --- | --- | --- |
| 开始调用 | 使用 | 创建任务并解析版本 |
| 创建个人草稿 | 修改 | 从一个已发布版本创建独立草稿 |
| 发起评审 | 提交修改 | 冻结待评审修订 |
| 提交反馈 | 请求修改 | 退回作者调整 |
| 使修改生效 | 批准并生效 | 校验、合并、生成版本并更新当前版本 |
| 处理分歧 | 解决修改冲突 | 展示原内容、我的修改和最新内容 |
| 查看发布记录 | 历史版本 | 查看内容快照、说明、作者和评审者 |

不要求用户理解 Git、分支、提交哈希、rebase 等术语。内部可采用相应实现。

## 3 待确认规则与建议默认值

以下规则是为了让开发方案可执行而提出的默认值，并非用户已经确认的决定。相关模块可以先开发通用机制，最终交互与测试预期应在确认后冻结。

| ID | 待确认事项 | 建议默认值 | 影响模块 |
| --- | --- | --- | --- |
| D1 | 会话版本选择从何时生效 | 只影响该会话的后续新任务，当前任务及其重试、恢复始终不变 | M5、M6 |
| D2 | 保留原版本的范围与期限 | 按会话、按 Skill 保留，直到用户选择新版或结束会话；新会话默认最新版 | M5、M6 |
| D3 | 用户没有处理提示时用哪个版本 | 不阻塞当前任务；后续新任务默认最新版；只有明确选择保留才固定旧版 | M5、M6 |
| D4 | 首次创建 Skill 如何生效 | 任意成员可创建草稿，需指定另一名维护者评审后首次生效；至少存在一位非作者维护者 | M1、M2、M4 |
| D5 | 编辑对象覆盖哪些文件 | 以 SKILL.md 及其受支持的引用资源作为完整版本；普通用户主要编辑说明，附件整体替换；脚本编辑权限沿用平台规则 | M2、M3、M7 |
| D6 | 谁能修改维护者 | 团队管理员配置，至少保留一位维护者；作者不能自审，无管理员绕过自审规则 | M1、M4 |

D1 与 D2 是最重要的发布前产品决策。会话保留旧版是“所有人默认使用新版”的显式例外，界面需要显示该例外，不能静默固定。

## 4 核心业务规则

### 4.1 版本与内容

- Skill 身份稳定，发布版本不可变；版本号建议先用顺序编号，不向非技术用户要求语义化版本分类。
- 每个版本保存完整内容清单及校验值，包含正文、引用文件和资源。运行中不得重新读取最新版正文或同名可变附件。
- 保存草稿不生成正式版本；批准并合并才生成正式版本。
- 历史版本可查看和比较，不提供任意历史版本全局固定的使用入口；会话保留已用版本是专门的交互。
- 恢复历史内容需要形成新的修改提案并再次评审，生效后产生新版本，不改写历史记录。
- 平台固定的是 Skill 包内容；外部 API、实时数据和外部模型输出不因此获得可重复性保证。

### 4.2 评审与合并

- 草稿记录创建时的基础版本。提交后形成不可变修订，评审针对该修订进行。
- 作者再次修改需要生成新修订，先前评审结果失效；不能评审 A 内容而生效 B 内容。
- “批准并生效”由非作者维护者执行，服务端再次校验权限、修订号和当前版本。
- 其他提案先合并导致基础版本落后时，对基础版本、当前版本和提案内容进行三方比较。
- 无文本冲突也应展示最终合并内容并要求维护者确认；有冲突则阻止生效，作者解决后重新提交。
- 不可文本合并的附件冲突需要选择保留哪一份或重新上传，不能覆盖丢失任一方内容。
- 同时合并的请求只能有一个基于同一当前版本成功；另一个进入重新比较流程。
- 数据库中的新版本、当前版本指针、提案合并状态和待广播事件要一起提交。广播暂时失败不能造成版本丢失或重复生效。

### 4.3 任务版本固定

- 在任务被接受并生成任务 ID 时，保存当时授权可用的 Skill 版本映射。该时刻为版本选择边界，排队等待也不改变映射。
- 默认映射来自任务启动时的当前版本；如 D1、D2 获确认，则应用当前会话显式保留的旧版选择。
- Agent 后续选择 Skill 时，只能从本任务映射解析；任务启动后才出现的 Skill 留给下一任务使用。
- 同一任务的多次调用、子任务、自动重试和断点恢复继承相同映射。子任务不得自行重新解析“最新版”。
- 用户显式重新发起任务生成新任务 ID，按当时会话策略重新解析版本；与系统自动重试区分。
- 版本与内容必须可读取且校验一致后才开始执行；失败时显示可重试错误，不能静默换版。
- 权限仍按现有平台规则校验，版本固定不意味着绕过权限撤销。这里的不中断保证针对正常 Skill 更新。

### 4.4 更新广播与会话提示

- 合并成功即更新平台的当前版本，并产生持久化更新事件；新任务是否采用新版不依赖浏览器收到事件。
- Skill 列表、详情和相关会话收到事件后刷新。未调用过该 Skill 的会话不显示更新提醒。
- 会话记录真实调用过的 Skill 和版本；不能仅凭“任务可用列表”把全部 Skill 当作已调用。
- 会话在第一次实际调用时也要比较当前版本，避免更新发生在调用记录写入之前而漏掉提醒。
- 提示文案应说明：“此技能已有更新，当前任务继续使用 vN。”并提供查看变化、后续任务使用新版、后续任务保留原版的操作。
- 保留原版时展示持续可见的版本标记和切换入口，具体行为按 D1 至 D3 定稿。
- 每个会话、每个 Skill 展示一条可更新提示。连续发布时更新到最新目标版本，避免堆叠多条提醒。
- 已显示 v2 提示后又发布 v3，用户点击使用新版时必须明确其确认的目标版本；如目标已过期，刷新差异并提示重新确认，不能默默把 v2 选择替换为 v3。
- 事件重复、乱序、浏览器断线或页面刷新后，状态应可通过服务端当前版本与会话记录重新计算；前端提示不是唯一事实来源。

## 5 数据对象与状态

| 对象 | 必要字段或约束 |
| --- | --- |
| TeamMember | 团队、用户、角色、有效状态 |
| Skill | 团队、稳定 ID、名称、描述、维护者、当前版本 ID、状态 |
| SkillVersion | Skill ID、版本序号、父版本、内容清单、校验值、变更说明、作者、评审者、生效时间；不可变 |
| Draft | 作者、Skill ID、基础版本、内容、草稿修订号、最后保存时间 |
| ChangeProposal | 草稿来源、基础版本、待评审修订、内容快照、修改说明、状态 |
| Review | 提案修订、评审人、结论、意见、时间 |
| TaskSkillSnapshot | 任务 ID、Skill 与版本映射、会话策略修订、创建时间；不可变 |
| SkillInvocation | 会话、任务、Skill、实际版本、调用时间与结果状态 |
| SessionSkillPreference | 会话、Skill、跟随最新或保留旧版、保留版本 ID、偏好修订号；按 D1、D2 定稿 |
| SkillUpdateEvent | 唯一事件 ID、团队、Skill、前后版本、递增序号、产生及投递状态 |
| SessionUpdateState | 会话、Skill、提示目标、已处理目标；支持去重与重建 |
| AuditLog | 操作者、团队、动作、对象、前后关联 ID、时间、请求 ID |

提案状态：草稿 → 待评审 → 已合并。待评审也可进入需修改、存在冲突、已拒绝或已撤回；需修改和存在冲突经新修订重新进入待评审。已合并不可撤销为草稿。

首次发布前的 Skill 不进入普通用户可用列表。已被任务引用的版本不能随普通内容清理删除。

## 6 模块化开发任务与完成条件

每个模块完成均要求：代码与接口可运行，权限在服务端校验，加载、空数据、失败及重试状态可用，相关自动化测试通过。下列完成条件是各模块额外必须满足的验收要求。

### M1 团队权限与维护者

依赖：平台身份体系。优先级：P0。

开发任务：

- M1.1 接入团队身份与成员角色，所有对象按团队隔离。
- M1.2 实现使用者、贡献者、维护者和管理员权限；同一人可兼任。
- M1.3 实现 Skill 维护者配置、变更及服务端操作授权。
- M1.4 实现作者禁止自审与无可用评审人的引导。

完成条件：

- 非团队成员无法通过列表、详情、历史、资源地址、事件或接口访问内容。
- 作者即使是维护者或管理员，也无法批准自己的提案。
- 无编辑权限的用户可以按授权使用，但不能保存或提交修改。
- 维护者资格在评审页面打开后被撤销，后续批准请求也会失败。
- 无合格评审人时明确提示配置维护者，不出现永久等待且无解释的流程。

### M2 Skill 列表详情与历史版本

依赖：M1、版本存储契约。优先级：P0。

开发任务：

- M2.1 建立完整 Skill 包、不可变版本和资源存储。
- M2.2 实现列表、名称搜索、详情和使用入口。
- M2.3 实现版本时间线、版本内容与两版本差异查看。
- M2.4 实现首次创建入口和基于历史内容发起恢复提案。

完成条件：

- 用户能从列表进入 Skill 并在 Agent 会话中发起使用。
- 历史显示版本号、生效时间、修改说明、作者和评审者。
- 发布新版后旧版正文和资源校验值保持不变。
- 首次发布前普通用户不能调用该 Skill。
- 恢复历史内容进入评审流程，原有历史记录不被覆盖。

### M3 独立草稿与修改提案

依赖：M1、M2。优先级：P0。

开发任务：

- M3.1 从发布版本创建个人草稿，保存基础版本及内容。
- M3.2 实现适合非技术用户的正文编辑、资源管理和预览。
- M3.3 实现自动保存、保存状态、离开提示与失败重试。
- M3.4 实现变更对比、修改说明、提交、撤回和重新提交。
- M3.5 使用草稿修订号保护同一用户多标签页编辑。

完成条件：

- 两人同时编辑同一 Skill，草稿互不覆盖，正式版本不受保存影响。
- 同一草稿在两个标签页被修改，过期保存请求被拒绝并保留用户输入。
- 保存失败显示失败状态，不能误显示已保存；刷新恢复最后成功保存的内容。
- 无变更或缺少修改说明不能提交，错误直接定位到可修正位置。
- 修改待评审内容会产生新修订，旧评审不能用于合并新内容。

### M4 评审冲突处理与原子合并

依赖：M1、M2、M3、M7 校验契约。优先级：P0。

开发任务：

- M4.1 实现待评审列表、差异详情、评审意见、请求修改、拒绝及批准并生效。
- M4.2 实现三方比较、文本合并与附件冲突识别。
- M4.3 实现冲突界面，保留基础、最新和个人修改供选择或编辑。
- M4.4 实现最终内容确认、并发版本检查、合并幂等及原子写入。
- M4.5 合并事务写入持久化事件，交由 M6 投递。

完成条件：

- 正常提案经非作者维护者批准后生成唯一新版本，并立即成为当前版本。
- 两提案同时合并不会丢失更新；后完成者需要基于最新内容重新确认。
- 不同位置改动可以形成候选合并结果；同段冲突阻止生效且不丢失任何一方修改。
- 冲突解决及内容变更后必须重新评审，之前的批准不能复用。
- 重复点击或请求超时重试不会重复生成版本和广播事件。
- 故障注入后不存在“提案已合并但当前版本没更新”或“版本已更新但事件永久丢失”。

### M5 Agent 运行时接入与任务版本固定

依赖：M1、M2、现有任务生命周期接口；会话偏好依赖 M6。优先级：P0。

开发任务：

- M5.1 在任务接受阶段原子确定 Skill 版本映射并持久化。
- M5.2 Skill 解析器按任务快照读取完整版本资源。
- M5.3 子任务、重试和恢复传递任务快照，记录真实调用版本。
- M5.4 在新任务中应用会话偏好，并区分重试与用户重新发起。
- M5.5 提供执行记录中的版本查看入口及资源读取失败反馈。

完成条件：

- 任务 T1 在 v1 生效时启动，v2 发布后 T1 后续调用、子任务和恢复仍使用 v1 全部资源。
- 无保留策略的新任务 T2 在 v2 生效后启动，使用 v2，即使浏览器没有收到广播。
- 排队中的任务按接受时快照执行，不因实际执行开始较晚而换版。
- 同一任务使用多个 Skill 时，全部按同一启动快照解析，避免运行期间逐个获取最新版。
- 每次调用记录可追溯到任务、Skill、版本和内容校验值。
- 缺失历史资源时明确失败，不回退到最新版继续执行。

### M6 更新广播与会话版本选择

依赖：M4 事件、M5 调用记录；最终交互依赖 D1 至 D3。优先级：P0。

开发任务：

- M6.1 实现事件投递、重试、去重、序号检查及失败可观测性。
- M6.2 将更新推送到有访问权限的相关在线客户端。
- M6.3 按会话实际调用记录生成更新提示和差异入口。
- M6.4 实现使用新版、保留原版和版本状态展示；选择写入服务端。
- M6.5 实现断线重连、重新打开会话和多标签页状态同步。
- M6.6 确保版本选择与任务创建并发时有明确顺序，任务记录实际使用的偏好修订。

完成条件：

- 已调用该 Skill 的会话出现更新提示，未调用的会话没有无关提醒。
- 当前任务不会因弹窗、选择、事件或页面刷新而切换版本。
- 按 D1 至 D3 的默认方案，选择保留后该会话下一任务使用旧版，另一会话下一任务仍用最新版；选择新版可解除保留。
- 用户不处理提示时当前任务继续运行，下一任务的行为与最终确认的 D3 一致。
- 连续发布只展示当前最新的有效提示，过期事件不能将提示退回旧版本。
- 断线期间发生更新，重连后可补齐提示；事件重复不会产生重复提示。
- 已打开的旧版提示在新版再次发布后不能导致静默采用未确认的版本。
- 不出现订阅开关、通知中心、外部消息发送或相关业务依赖。

### M7 内容校验审计与运维

依赖：贯穿 M1 至 M6。优先级：P0。

开发任务：

- M7.1 在提交和合并前检查 Skill 格式、必要字段、引用文件、资源完整性及平台支持的文件类型。
- M7.2 若平台已有测试能力，提供对待评审固定内容的试运行；运行仍遵守平台现有权限。
- M7.3 记录创建、提交、评审、合并、恢复、维护者变更和会话版本选择审计。
- M7.4 监测合并失败、事件积压、投递延迟、解析失败与版本不一致。
- M7.5 建立被任务引用版本的保留策略，以及存储和数据库备份恢复验证。

完成条件：

- 缺失引用文件、无效格式或不支持资源不能合并；界面指出具体问题。
- 审计可追溯谁让哪个内容生效，日志不包含平台密钥或无关的会话敏感内容。
- 投递故障能被发现并重试；恢复后无重复版本或用户选择丢失。
- 备份恢复演练后，进行中任务的版本映射与资源仍能正确解析。
- 自动化覆盖授权、并发合并、旧任务隔离、重试恢复和事件补偿；格式校验通过不能被表述为 Skill 效果已经验证。

## 7 接口契约要求

具体路由和框架由实现决定，但模块间必须约定以下能力。

| 能力 | 输入与并发保护 | 输出或约束 |
| --- | --- | --- |
| 保存草稿 | 草稿 ID、预期修订号、内容 | 新修订号；过期请求返回可恢复冲突 |
| 提交修改 | 草稿修订、修改说明、幂等键 | 不可变待评审修订 |
| 批准并生效 | 提案修订、预期当前版本、确认后的合并内容标识、幂等键 | 新版本或需重新比较；不静默覆盖 |
| 获取版本差异 | Skill ID、两个版本或修订 ID | 正文和资源的增加、删除与修改 |
| 创建任务快照 | 会话、任务 ID、可用 Skill 范围 | 持久化版本映射及会话偏好修订 |
| 读取执行内容 | 任务 ID、Skill ID | 对应版本的完整内容及校验值 |
| 设置会话偏好 | 会话、Skill、策略、目标版本、预期偏好修订 | 服务端保存结果与影响范围 |
| 重建会话提示 | 会话、已知事件序号 | 当前有效提示与版本选择状态 |

错误类型至少区分：无权限、修订过期、合并冲突、内容校验失败、资源缺失、暂时不可用。客户端应显示下一步操作，不直接输出内部错误堆栈。

## 8 交付顺序

| 阶段 | 交付模块 | 阶段出口 |
| --- | --- | --- |
| A 基础契约 | M1、M2 存储、M5 生命周期契约、M7 校验契约 | 能创建不可变版本，明确任务边界和身份权限 |
| B 修改到生效 | M2 界面、M3、M4、M7 基础审计 | 用户可提交，维护者可评审，冲突可解决，新版本可生效 |
| C 运行时隔离 | M5、M7 恢复验证 | 真实 Agent 任务在更新前后正确隔离版本 |
| D 会话更新 | M6、M5 会话策略接入 | 更新提示、用户选择、重连补偿形成完整闭环 |
| E 发布验收 | 全模块 | 第 9 节场景通过，关键产品规则确认，故障监测可用 |

M7 贯穿各阶段。不得等界面完成后才决定任务快照的存储与生命周期，否则无法可靠兑现不中断要求。

## 9 端到端验收场景

| ID | 场景 | 预期 |
| --- | --- | --- |
| E1 | A、B 同时从 v1 修改，A 先合并 | B 提交或合并时发现基础版本落后；所有改动可恢复 |
| E2 | A、B 修改同一段文字 | 阻止自动生效，解决冲突后重新评审 |
| E3 | 作者具有维护者或管理员身份 | 自审请求仍被服务端拒绝 |
| E4 | 评审页面打开后作者提交新修订 | 旧页面的批准请求失效，不发布未审内容 |
| E5 | T1 执行时 v2 生效 | T1 的后续调用、子任务、重试和恢复继续用 v1 |
| E6 | v2 生效后启动 T2，客户端尚未收到事件 | T2 默认使用 v2 |
| E7 | 调用过 v1 的会话收到 v2 提示并选择保留 | 当前任务不变；后续任务按已确认的会话策略执行 |
| E8 | 保留 v1 后另开新会话 | 新会话默认使用当前最新版 |
| E9 | 会话断线期间 v2、v3 连续生效 | 重连后提示最新有效版本，没有重复弹窗或版本倒退 |
| E10 | 用户看着 v2 提示时 v3 生效，再点击新版 | 明确刷新目标与差异，不偷偷将 v2 确认当成 v3 确认 |
| E11 | 数据库提交成功，事件投递服务故障 | 新任务仍用新版；投递恢复后补齐会话提示 |
| E12 | 合并请求超时后客户端重试 | 只生成一个版本和一个逻辑更新事件 |
| E13 | 正文未改但附件或脚本更新 | 旧任务仍读旧附件，新任务读新附件 |
| E14 | Skill 更新先于会话第一次调用记录写入 | 记录实际调用后仍能发现并提示版本落后 |
| E15 | 任务启动与用户选择保留版本同时发生 | 任务快照对应一个明确已提交的策略，不出现部分 Skill 切换 |

## 10 质量目标与发布门槛

以下性能数字为建议验收基线，需结合现有平台容量确认，不代表现有性能测量结果。

- 正常网络与服务健康状态下，合并提交到相关在线会话提示可见，端到端 P95 不超过 3 秒；断线重连完成后 5 秒内完成状态核对。
- 新任务采用哪个版本由服务端一致性保证，不允许等待上述广播时间窗口才能生效。
- 并发与恢复测试中，进行中任务意外切换版本、丢失已提交内容、越权发布均为零容忍缺陷。
- 负载测试建议先按单团队 100 个在线会话、1,000 个 Skill、同一 Skill 10 个独立提案建立基线；目标规模需实施前确认。
- 自动化必须覆盖 E1 至 E15；涉及 D1 至 D3 的断言在产品确认后冻结。
- 发布前完成真实 Agent 环境验收，不以模拟任务代替 M5 验收。
- 发布前确认 D1 至 D6，记录现有平台任务接受、子任务、重试、恢复和资源读取接口，并确认团队身份接入方式。
